# Security model

Human users authenticate with random bearer tokens; only SHA-256 digests are stored. Sessions expire after 12 hours. API tokens inherit the user's current role and can be revoked. Passwords use salted scrypt; never stored or returned in plaintext. Admin bootstrapping requires a password of at least 12 characters. `make init` generates random credentials rather than shipping a shared login.

RBAC roles: viewer reads projects/jobs/logs/schedules/workers, operator adds projects/deployments/runs/schedules, admin additionally manages users, encrypted environments, registry credentials, auditing, and deletion. This first release has workspace-wide roles, not per-project tenancy. Secrets use Fernet authenticated encryption with an externally configured key. The UI shows secret names only. Agent authentication is separate from user tokens. Agents are trusted infrastructure; the shared agent credential allows access to job secrets and execution callbacks. Per-agent credentials, mTLS identity, SSO, rate limiting and scoped tokens are future hardening work.

The API and frontend never mount Docker sockets. Docker TLS client keys are read-only in the builder and worker. The Compose engine has no published port and lives on a separate internal service network. Only trusted administrators should access this engine. Worker containers have no Docker socket, run as UID 65532, drop all capabilities, deny privilege escalation, limit memory/CPU/PIDs, and use a read-only filesystem with writable `/tmp`. Custom images must make their working directory readable to that UID. Projects needing persistent filesystem writes require adapting their output destination; arbitrary host mounts are intentionally unavailable.

Archive extraction is bounded and rejects traversal, links, devices, duplicate paths, excess bytes and excess file counts. API validation never executes uploaded code. Docker builds happen in the separate builder agent's engine. Build execution is not a complete hostile-code sandbox: use separate infrastructure for untrusted projects. See [Docker Engine security](https://docs.docker.com/engine/security/) and [runtime restrictions](https://docs.docker.com/engine/containers/run/) when hardening the deployment.

Configured secret values are redacted from archived execution logs; package/proxy build arguments are redacted from archived build output. Arbitrary source-generated secrets, transformed values, spider arguments, user-provided settings, and secrets baked into images cannot be automatically recognized. Do not pass passwords as spider arguments. Build artifacts, logs and database backups must remain private. Do not enable third-party analytics in an air-gapped installation.
